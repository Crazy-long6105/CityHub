# 模块一：秒杀资格与异步订单可靠性设计

日期：2026-10-18。状态：讨论方案已确认，本文待整体审阅；尚未修改业务代码。

## 1. 目标与范围

本阶段完成 Redis 资格预扣、Kafka 异步下单、消费幂等、结果查询和异常请求恢复，支撑简历中的秒杀防超卖、一人一单和异步订单处理。

接口成功受理不等于订单创建成功，更不等于付款成功。同一用户、同一张券最多占用一个有效购买资格；请求处理中、待支付、已支付时不允许再次抢购。未支付订单确认关闭并完成资格释放后，允许使用新订单号重新抢购。

支付接口、待支付订单超时关单、缓存体系和限流组件分别在后续模块讨论。本阶段的“终止请求”仅针对尚未成功创建的订单，不操作已经创建的待支付订单。

## 2. 已选择的方案及取舍

| 问题 | 选择 | 原因与代价 |
|---|---|---|
| 接口承诺 | 可靠受理后异步创建订单 | 减少同步数据库操作，需要结果查询 |
| Redis 资格结构 | 每张券的 Hash：用户 ID -> 订单号 | 资格与订单绑定，避免旧补偿误删新资格 |
| 请求恢复记录 | Redis 请求 Hash + 待处理 ZSet | 与库存预扣在同一段 Lua 中写入；恢复能力依赖 Redis 数据存续 |
| 数据库防重复购买 | 独立 MySQL 购买资格表 | 比历史订单永久唯一约束更适合关单后重购；增加一张表 |
| 消息发送结果未知 | 保留资格，有限恢复，按订单号查结果 | 不能因超时就释放；故障时最终结果可能延后 |
| 阻止迟到消息 | 同订单号的数据库终止记录 | 与订单创建通过主键竞争；异常收尾需要访问数据库 |

未选择请求内同步落库、MySQL Outbox、单纯依赖内存重试或永久等待消息恢复。Kafka 采用至少一次处理思路，通过数据库事务、唯一约束和幂等补偿实现业务效果去重，不承诺跨 Redis、Kafka、MySQL 的分布式原子提交。

## 3. 响应与时间约定

统一以 Redis 预扣成功时间为起点，保存不可变的创建时间与截止时间。订单号作为字符串传递，避免前端大整数精度丢失。

| 时间或结果 | 系统行为 | 用户语义 |
|---|---|---|
| 前 1 秒 | 尝试发送，有限等待 Broker 确认；包括同步发送准备时间和请求内重试预算 | 确认接收则已受理，否则根据确定性返回失败或确认中 |
| 1 至 10 秒 | 异步消费、有限恢复 | 处理中；不承诺消费者已经开始执行 |
| 10 至 30 秒 | 继续恢复，降低前端轮询频率 | 处理较慢 |
| 达到 30 秒 | 停止主动重发，触发数据库终止确认 | 已存在订单则成功，否则争取安全终止 |
| 数据库终止已提交且 Redis 补偿完成 | 返回终态 | 创建失败，可以重新抢购 |
| 数据库不可用或提交结果未知 | 延后收尾，限速重试 | 结果暂未确认，可离开页面稍后查看 |

30 秒是创建请求的处理期限，不是待支付订单有效期，也不是极端故障下的最终确认时限。消费者发现请求已到期时不启动新的创建事务；期限前已开始的事务可能稍后提交，由数据库主键竞争结果决定成功或终止。

接口应返回订单号、受理状态和可查询结果，而非仅返回订单号。传输已确认但数据库已经更快地产生终态时，优先展示终态。Redis 预扣超时属于“受理未确认”，与预扣已完成后的 Kafka“结果确认中”分开，按第 5 节处理。

## 4. 数据职责

### 4.1 Redis

| 数据 | 内容与职责 |
|---|---|
| 活动信息 | 开始和结束的毫秒时间戳；活动初始化时写入 |
| 预扣库存 | 独立整数，表示还能接受多少份购买资格 |
| 购买资格 Hash | 用户 ID -> 当前占用资格的订单号 |
| 请求记录 | 订单号、用户、券、创建/截止时间、发送状态、处理结果、重试信息、失败原因 |
| 待处理 ZSet | member 为订单号，score 为下次检查时间；仅包含未完成或待补偿请求 |

控制库存与展示缓存分开命名和管理。普通缓存更新、删除消费者不得覆盖或删除控制库存、购买资格和请求记录。活动已经接收请求后，禁止以数据库剩余库存直接覆盖 Redis 预扣库存。

活动信息缺失、控制库存缺失或数据类型异常时拒绝受理，不自动重置库存。未完成请求和有效资格不设置固定 30 分钟 TTL；成功或失败的请求记录在确认完成后才进入可配置保留期。已支付购买资格至少保留到活动停止受理，不随请求记录过期而消失。

本阶段基于当前单 Redis 实例设计，不声明 Redis Cluster 支持。脚本显式传入访问的 Key；若迁移 Cluster，需另行设计同槽及待处理索引分片。

### 4.2 MySQL

新增 `tb_voucher_purchase_qualification`，核心字段为 `user_id`、`voucher_id`、`order_id`、`create_time`。`(user_id, voucher_id)` 唯一，`order_id` 唯一，确保一份有效购买资格只对应一笔订单。

`tb_voucher_order.id` 继续作为请求和订单的唯一标识。新增独立的“创建失败”状态及失败原因，不复用现有“已取消”来混淆从未扣过数据库库存的请求。具体状态编码和迁移 SQL 在实现计划中与现有 1 至 6 编码核对。

创建失败记录不占数据库购买资格，也不扣数据库库存。有效订单保留数据库资格；后续关单模块在同一数据库事务中关闭订单、回补数据库库存，并按订单号删除对应资格。创建失败记录不得进入待支付、支付和关单业务。

## 5. 原子预扣与幂等释放

预扣 Lua 先检查参数和 Key 类型，再检查活动时间、库存及用户资格；通过后扣减一份库存，绑定用户和订单号，创建请求记录并加入恢复索引。使用 Redis 时间和预存时间戳，修复现有 `require`、`os.time()` 和返回值类型问题；返回明确状态码，订单号由调用方事先生成。

为收敛预扣调用自身超时的情况，在调用前另外生成短期的“允许首次预扣截止时间”，它不同于预扣成功后开始计算的 30 秒创建期限。初始预扣许可窗口为 1 秒，应用与 Redis 使用同步的 UTC 时钟；Lua 对已有同订单号请求返回原结果，对新的预扣先校验许可是否已到期，过期则不执行任何预扣。

返回的查询凭据绑定订单号、当前用户、预扣许可截止时间和凭据有效期，使用服务端签名防止客户端伪造或延长许可。Redis 预扣超时后，先显示“受理未确认”；查询用只读 Lua 原子取得请求记录和 Redis 时间，发现记录则进入正常处理；仅在凭据仍有效、记录缺失且 Redis 时间已超过许可截止时间时，才可确认“未受理”，允许重试。此时排队的旧 Lua 即使迟到也会因许可到期而拒绝执行。许可未到期或 Redis 仍不可用时保持未确认。

查询凭据有效期初值为签发后 24 小时，终态请求记录从完成时起至少保留 24 小时，且不得早于关联查询凭据到期时间删除；未完成记录继续保留。凭据过期后的记录缺失只能表示“查询凭据或记录已过期”，不能判为从未受理，也不能触发库存释放。保留时长可联动调整，必须维持上述覆盖关系。

若 Lua 确实预扣成功，请求和恢复索引已在同次执行中写入，应用重启后仍可恢复；若根本未执行，则没有占用库存，也不需要后台凭空发现一个不存在的请求。上述缺失判断以 Redis 数据未丢失为前提，整体数据丢失按第 8 节停止受理并核对处理。此预扣超时协议为文档审阅时补充的技术边界，须一并审阅。

Lua 的原子执行不代表运行错误时会回滚已经执行的写入，因此参数、数据类型和可预见错误应在写入前校验，并覆盖故障测试。Redis 资源不足等非业务故障须停止受理并核对数据，不能声称任何脚本错误都自动恢复。

同一笔请求的消息重发复用订单号，不重新预扣。用户重新调用接口而已有资格时，返回该资格对应的原订单号及处理结果，不创建第二份请求。只有旧资格已释放后，才允许新订单号重新预扣。

释放 Lua 仅在资格仍绑定待释放订单号时回补一份库存并删除资格；重复执行或归属不符时不加库存、不删除其他订单资格。失败结果和恢复索引的收尾也采用条件更新；旧订单结果不覆盖新订单记录。

任何可能已有消息在途的请求，包括恢复任务曾经发送过的请求，释放前必须先取得数据库终止依据。只有能够证明请求从未发出、也没有并发发送者时，才可走直接回退；实现初期统一经数据库终止流程处理预扣后的失败，避免依赖不可靠的异常分类。

## 6. Kafka 发送与数据库消费

发送消息包含订单号、用户 ID、券 ID、创建时间和截止时间；重发保持业务字段不变，以订单号作为消息 Key。显式配置适配当前 Spring Kafka 版本的 JSON 序列化、Broker 确认、发送与投递超时。发送调用返回不等于 Broker 确认，线程等待超时不等于消息没有入队。

发送状态与业务结果分开：发送状态可为待发送、已确认、未知；业务结果为处理中、终止确认中、成功、失败。迟到的发送成功或失败回调只能更新发送信息，不能覆盖数据库已经确定的业务终态，也不能延长截止时间。

消费者核对请求身份、不可变参数和期限；请求记录不可用时不凭客户端消息猜测创建。正常创建由 Spring 代理生效的数据库事务执行，顺序为：

1. 插入使用原订单号的待支付订单，尚不提交。
2. 插入购买资格，利用用户与券的唯一约束兜底。
3. 执行 `stock = stock - 1 WHERE voucher_id = ? AND stock > 0`，校验影响行数。
4. 一起提交；任一步失败则回滚全部数据库修改。

订单主键冲突在事务结束后读取数据库已提交状态：有效订单按幂等成功处理，创建失败记录按终止处理；不能在已回滚的事务中继续写结果。资格冲突、数据库库存不足等确定业务失败，回滚后另行终止当前请求。死锁、锁等待超时和数据库不可用属于暂时故障，不能直接当作购买失败。

事务提交后更新 Redis 结果，再确认 Kafka 消息。若 Redis 更新失败，重投或恢复任务根据数据库结果继续收尾，不重复扣库存。消费异常不能只记录日志后继续提交后续 offset；需要版本兼容的有界重试、失败消息隔离或暂停策略，并由 Redis 恢复索引继续追踪业务结果。失败消息进入隔离队列本身不等于订单业务已经失败。

## 7. 超时终止与故障恢复

终止任务使用同一订单主键插入“创建失败”记录并提交。若正常创建事务已经提交，则主键冲突后认定订单已创建，不能补偿；若创建事务尚未结束，竞争等待后以提交结果为准。若终止记录先提交，迟到消费者的订单插入失败，不会创建资格或扣库存。

数据库终止提交后，依次完成 Redis 幂等释放、请求失败终态和恢复索引移除。若数据库提交结果未知，保持确认中；若 Redis 收尾失败，保留恢复任务并重试。成功终态不释放购买资格。

后台只从 ZSet 按到期时间取有限数量任务，不全量扫描 Redis，也不因前端轮询而查 MySQL。任务使用短租约减少多实例重复执行，但正确性依靠条件更新、数据库约束和 Lua，不能只依赖租约。工作线程数、批量大小和数据库访问预算均有上限；数据库故障采用退避重试。

发送未确认的请求在 30 秒内有限重发；已确认入队的请求优先等待消费，到期后再核对终态。重试间隔、批量上限、工作线程数和消息隔离配置将在实现计划中给出初始值，并通过测试调整。调度不得在消费线程中长时间休眠。

恢复覆盖：预扣后尚未发送应用就重启、消息已入队但确认丢失、数据库提交后 Redis 未更新、终止提交后资格未释放、补偿完成后任务未移除。多次执行恢复不改变已有业务终态。

## 8. 查询、运行边界与改动范围

新增登录用户自己的请求结果查询接口，按订单号及签名凭据读 Redis 并核对用户归属；普通轮询不查 MySQL。记录缺失不能等同订单创建失败，也不能据此自动回补库存；仅符合第 5 节预扣许可到期条件的请求可判为未受理。终止记录在可能的消息重放期间不得删除；主动重放历史消息时还须满足期限与终态检查。

Redis 是控制库存和恢复索引的存储，AOF 配置与实际刷盘策略需要核对。默认异步持久化不保证已返回的每笔受理在 Redis 整体数据丢失后仍可恢复。Redis 数据丢失或控制数据被清空时停止活动受理，核对数据库有效订单、资格及在途请求后再恢复，不能简单重建一个满库存。更强的数据灾难恢复承诺需要另行设计。

改动集中在秒杀初始化、订单 Service/Controller、Lua、请求/消息 DTO、Kafka 消费与配置、恢复任务、订单 Mapper/状态、购买资格实体与表结构。移除订单创建后异步回写控制库存的逻辑；展示缓存重构留在后续缓存模块。

提供非破坏性增量 SQL，不要求重新导入包含删表语句的完整 SQL。旧 Set 与新 Hash 使用隔离的 Key 命名；活动切换前停止旧生产者、排查旧消息并处理既有订单资格，不能直接把旧 Set 当 Hash 读取或在运行中重置预扣库存。自动迁移历史有效资格前必须核对是否已有重复购买。

## 9. 分阶段修改与验收

业务实现按下列三个检查点推进，每阶段检查通过后再进入下一阶段，不一次性扩展到支付、缓存或限流。

| 阶段 | 修改目标 | 核心验收 |
|---|---|---|
| 1. 资格预扣 | 控制库存隔离、时间戳、Hash 归属、请求和恢复索引、释放 Lua | 库存 10 并发请求只接受 10 份资格；同用户只占一份；旧释放不影响新订单；重复释放只回补一次 |
| 2. 事务与幂等 | 购买资格表、创建事务、终止记录、重复消费 | 同订单重复消费只扣一次；同用户不同订单只能成功一笔；中途故障全部回滚；创建和终止竞态只有一种结果 |
| 3. 受理与恢复 | Kafka 确认、期限、恢复任务、结果查询、异常消息处理 | 预扣后重启能恢复；确认丢失不误释放；提交后 Redis 故障可恢复；终止后迟到消息不创建订单 |

额外验证正常轮询不产生数据库查询；故障积压时恢复任务受并发和批量上限约束；达到 30 秒停止主动发送；数据库不可用时不假报失败；状态查询不能读取其他用户请求。预扣调用超时分别验证实际已执行和根本未执行两种情况，以及许可到期后的旧 Lua 不能新增预扣、查询与预扣竞态不会误报未受理、查询凭据不能被伪造或延长、终态记录保留期与查询凭据到期边界不会把成功请求误判为未受理。

使用真实 Redis 验证 Lua 并发与数据类型，使用 MySQL 验证事务和唯一约束，使用 Kafka 验证确认丢失、重复投递与消费异常；纯 Mock 测试不能作为跨组件正确性的唯一证据。性能改善只在完成对比压测后给出数字，不以设计推断代替实测。
