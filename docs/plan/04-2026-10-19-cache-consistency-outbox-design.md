# 模块四：缓存一致性与消息补偿设计

日期：2026-10-19。

状态：核心方案已逐项讨论确认；本次整理技术衔接、方案对比及验收清单，待整体审阅。尚未修改业务代码或执行功能测试。

## 1. 目标和一致性边界

商家信息写入 MySQL 后，可靠地失效商家详情 Redis 缓存。数据库是事实来源；缓存由查询重新构建，消息不携带商家旧快照覆盖缓存。

本模块采用最终一致性：数据库提交与 Redis 失效之间允许短暂旧值；已经读到旧值的请求也可能继续返回旧值。依赖恢复、后台处理继续运行且持久化待办保留时，未完成失效最终能够恢复执行。不承诺所有更新后的读取立即看到新数据，也不承诺依赖持续故障时的固定收敛时间。

沿用模块三的决定：真实商家缓存仅有 30 分钟逻辑有效期，没有物理 TTL，也不额外设置旧值使用上限；空值缓存仍有 2 分钟物理 TTL。因此本模块不再宣称“TTL 兜底保证一致性”。逻辑刷新有助于正常恢复，但不能替代可靠失效待办。

模块顺序保持为 01 秒杀资格与异步订单可靠性、02 支付与超时关单、03 缓存穿透与逻辑过期、04 缓存一致性与消息补偿、05 Caffeine + Redis 二级缓存、06 多维度滑动窗口限流。

## 2. 现有代码与缺口

- `ShopServiceImpl.update` 在事务方法内部更新数据库并立即 DEL，真正的事务提交发生在方法返回后，不能把 SQL 执行成功等同于事务提交成功。
- `updateById` 的业务结果没有核对，可能对未实际更新的对象也返回成功。
- 商家更新入口没有接入现有 `CacheManager` 消息补偿工具。
- `CacheManager` 直接调用异步 `send` 后记录发送成功，未以 broker 确认为依据；同步 try/catch 无法覆盖所有异步发送失败。
- `CacheCleanListener` 删除失败也确认消息；现有说法依赖 TTL，但与模块三的真实缓存策略不符。
- `CacheUpdateListener` 的失败路径休眠后没有实际重新发送，再确认消息，不能形成可靠重试。
- 现有缓存更新消息可携带数据覆盖缓存，迟到的旧快照可能覆盖新缓存；不采用它作为商家一致性方案。

## 3. 已确认的核心选择

| 问题 | 决定 |
|---|---|
| 何时失效缓存 | 数据库事务明确提交成功之后 |
| 数据库已提交、Redis 失效失败 | 更新接口仍返回更新成功；后台补偿 |
| 提交后进程退出、尚未发消息 | 同一数据库事务保存 Outbox 待办，恢复后继续投递 |
| 消息更新还是删除缓存 | 只做失效；重建读取数据库 |
| 与在途重建竞争 | Lua 原子删除缓存、撤销当前重建锁，并清理该商家刷新退避标记 |
| 何时完成待办 | Redis 失效操作确认成功后；Kafka 接收成功不算完成 |
| 重试职责 | 数据库保存进度与时间，后台扫描投递，Kafka 消费者一次领取执行一次 |
| 失败重试 | 1 秒、5 秒、30 秒，之后每 60 秒；可配置，不阻塞消费线程休眠 |
| 是否重试到次数上限就删除 | 不删除未完成待办；持续失败报警，限制处理并发 |
| TTL 取舍 | 不新增真实数据物理 TTL，相应调整简历表述 |

这里的 Outbox 就是与商家修改一起提交的持久化待办，并非 Redis 与 Kafka 自动加入了 MySQL 事务。

## 4. 写入事务与提交后快速失效

写入步骤：

1. 校验参数及现有商家的存在性，按实际 SQL/驱动语义区分不存在、未改变与更新失败，不能忽略业务结果直接报成功。相同值重复更新无需保证整条接口只执行一次；多生成一条失效任务仍然安全。
2. 在同一个 MySQL 事务内更新商家，并插入一条商家失效待办。待办保存失败则商家修改也回滚，不能在缺少恢复依据时提交。
3. 事务提交明确成功后，尝试取得该待办的短租约，执行一次同步快速失效；成功再独立标记待办完成。
4. Redis、领取或完成更新失败，由持久化待办继续恢复，不把已经提交的商家修改改报失败。

实现采用独立事务服务 Bean 或明确的事务模板，确保对外编排逻辑在实际事务提交完成后才进入 Redis 分支；不依靠同类内部调用的事务注解。若使用提交后回调，它只做快速触发，不能替代扫描恢复；回调中的数据库任务状态更新必须使用新的短事务，不能假设原事务仍可写入提交。

快速路径使用短 Redis 调用超时，沿用模块三建议的 200 毫秒初始命令超时，并核对客户端有效配置；它不是接口整体耗时承诺。不在请求线程中循环重试或等待 Kafka 消费。数据库提交结果未知时进入确认/重试核对，不能把未知结果当作明确提交成功；本阶段不为商家更新额外承诺请求级业务幂等键。

新增商家也通过事务服务同时保存失效待办，清理先前可能存在的空值标记。当前没有删除商家入口，不新增删除功能；未来新增删除或其他详情写入口时必须沿用相同协议，不能绕过待办与失效流程。GEO、列表索引维护不在本模块范围。

## 5. 失效与在途重建的协调

模块三已经约定：重建任务拿到每次不同的 token，只有 Lua 确认锁仍属于本次 token，才能发布真实缓存或空值缓存并释放锁。

本模块增加一个权威失效 Lua，在同次执行中删除：

- 对应商家的详情缓存。
- 对应商家的当前重建锁。
- 对应商家的短暂刷新失败退避标记。

普通任务释放锁仍只能释放自己的锁。只有服务端可信的商家失效操作允许主动撤销当前重建资格，不能把这个权限暴露为客户端随意传 Key 的接口。

对于“任务 A 读旧值，写请求 B 提交新值，A 迟到发布”的竞争：

- A 在失效 Lua 之前完成发布，随后其缓存被 Lua 删除。
- A 在失效 Lua 之后发布，原锁 token 已不存在或属于新任务，发布 Lua 拒绝写入。
- 失效后取得新锁的任务必须重新读取已提交数据库，不复用旧任务的查询结果。

缓存回源使用 MySQL 主库的一次独立、短读取，不沿用写请求之外已经建立旧快照的长事务，也不接入有延迟的只读副本。先取得重建资格，再执行数据库查询，真实值与空值都遵守发布资格校验。否则仅撤销锁不能解决“新任务仍从旧快照读取”的问题。

失效 Lua 确认执行成功，即使 Key 原本不存在，也可视为完成。调用超时不能断言未执行，按未完成保留任务并重试。Lua 保持短小，校验参数后再变更；沿用项目当前单 Redis 实例范围，不声称支持跨槽多键执行。

失效是允许重复的：不会恢复旧数据，但可能额外删除新缓存、撤销新重建并产生一次重建开销。因此已完成待办的重复消息应尽早跳过；并发和响应丢失仍可能导致少量重复失效，不承诺零额外重建。

## 6. MySQL 待办表及状态

新增独立的 `tb_cache_invalidation_task`，不把缓存工作与模块二订单库存补偿表混用。建议字段：

| 字段 | 用途 |
|---|---|
| `id` | 本次失效事件的唯一编号，也是 Kafka 任务标识 |
| `business_type`、`business_id` | 当前固定商家详情与商家 ID，服务端据此推导允许操作的 Key |
| `status` | 待执行 PENDING、执行中 RUNNING、已完成 DONE |
| `retry_count`、`dispatch_retry_count`、`next_execute_time` | Redis 执行与 Kafka 投递各自的失败次数、允许下一次实际执行的时间 |
| `next_dispatch_time`、`dispatch_token` | 下一次允许投递的时间、本轮投递标识，控制多实例重复发送及迟到回调 |
| `claim_token`、`lease_until` | 本次执行领取标识、租约截止时间 |
| `last_error`、`create_time`、`update_time`、`completed_time` | 排障、恢复和积压观察 |

主键保证事件唯一；每次成功写入产生新事件，不能对商家 ID 建永久唯一约束，否则可能吞掉后续修改。建议索引为 `(status, next_dispatch_time, id)` 和 `(status, lease_until, id)`，支持投递扫描及过期执行恢复。记录中不保存商家 JSON 快照，不允许由消息任意指定 Redis Key。

新待办初始为 PENDING，执行与投递时间均设为当前数据库时间，事务提交可见后即可处理。所有领取、预约和租约时间使用数据库时间，避免不同应用节点时钟偏差造成提前领取。

任务状态与投递状态不同：发送成功后可以仍为 PENDING；RUNNING 只表示当前工作者领取了执行资格；只有确认 Redis 失效成功才转为 DONE。

## 7. 后台投递、消费和重试协议

### 7.1 后台投递

后台每秒扫描一次到期 PENDING 待办，候选同时满足下一次执行与投递时间到期；每批候选最多 100 条，单实例投递工作并发初值为 2。真实吞吐和全实例预算由压测确定。

通过短数据库条件更新竞争投递资格：匹配待执行状态及到期时间，记录新 `dispatch_token`，并先将下一次投递时间推迟 30 秒，作为有界投递预约。只有更新成功者发送，数据库事务不跨越 Kafka 网络调用。投递后中途退出，预约到期仍能重新扫描；预约不是永久“已发送”状态。

Kafka 消息只含任务 ID、协议版本及必要业务标识，分区 Key 使用商家 ID。消费者以数据库待办内容为准并核对消息标识。统一 JSON 序列化，沿用模块一完善生产者确认、超时和错误处理；异步 send 返回不代表 broker 已接收。

broker 确认只记录投递结果，不能完成待办。发送明确失败或结果未知，增加独立的 `dispatch_retry_count`，按 1 秒、5 秒、30 秒、随后 60 秒退避更新投递时间；仅在状态仍为 PENDING 且 `dispatch_token` 匹配时更新，不能覆盖已被领取、已完成或新一轮投递的进度。消费者一旦领取就清除旧 `dispatch_token`，阻止迟到的发送回调干扰执行结果。

broker 已接收但迟迟未消费，未完成任务在投递预约到期后可以重投。允许至少一次投递，不追求跨 MySQL/Kafka/Redis 的恰好一次；预约窗口减少重复，不承担正确性保证。

### 7.2 消费与直接执行共用领取逻辑

直接失效和消息消费都通过同一个执行服务领取待办：匹配 PENDING 且 `next_execute_time` 到期，改为 RUNNING，生成新 `claim_token` 并设置 30 秒租约。消费不受 `next_dispatch_time` 约束，否则发送预约会挡住刚发出的消息。

已 DONE 的任务跳过；已有有效执行租约的任务不重复执行；尚在失败退避期的任务不提前执行。领取成功后只尝试一次 Redis Lua，再以 `claim_token` 和 RUNNING 状态为条件记录完成或安排重试。执行 Redis 期间不保持数据库事务或行锁。

失败时写回 PENDING，递增重试次数并记录错误；将下一次执行时间与投递时间设为退避到期，清除旧执行与投递标识。间隔为 1 秒、5 秒、30 秒，之后 60 秒，作为初值。执行者退出导致 RUNNING 租约过期时，扫描器通过状态及过期条件 CAS 恢复 PENDING，清除旧领取与投递标识，安排立即执行和投递；不能让运行中任务永久失联。

租约到期后旧执行者即使回来，也不能覆盖新执行者的数据库状态。旧 Redis 调用仍有可能迟到执行一次失效，此副作用仍然安全但可能导致额外重建。不能把短租约说成杜绝所有重复执行。

### 7.3 消费确认与异常

成功执行并持久化 DONE 后，可以确认 Kafka 消息。失败后将下一次重试安排可靠保存到数据库，也可以结束本次消息，因为恢复依据已存在。数据库确认已完成、存在有效租约或已有未来退避安排时，重复消息可跳过并确认。

读取数据库失败或无法确认任务状态、保存重试安排失败时，不走无条件确认的 catch 分支。由消费容器异常处理暂停/重投并报警，同时由持久化任务及租约恢复兜底；不得手动继续提交后续偏移量来掩盖本次失败。消费者不自己再发重试消息，也不 Thread.sleep 等待退避。

格式错误或未知协议不阻塞整个分区无限循环；记录并进入可追踪的异常隔离通道，隔离成功才能结束该记录，合法未完成任务仍由扫描恢复。消息对应任务缺失要先区分已清理的历史 DONE 与数据异常：已完成记录至少保留 7 天，长于当前 24 小时消息保留期，并结合消费积压检查再清理；超出正常消息保留期的人工重放须专项核对。正常保留窗口内任务缺失视为异常，不静默认定失效已成功。

## 8. 故障窗口和恢复依据

| 故障点 | 处理 |
|---|---|
| 商家更新或待办插入失败 | 同一事务回滚，不发失效 |
| 数据库提交后、快速删除前退出 | PENDING 待办由扫描找到并投递 |
| 快速执行取得租约后退出 | 租约到期后恢复 |
| Redis 成功、完成任务前退出 | 待办恢复后重复失效，不丢工作 |
| Kafka 不可用或投递响应丢失 | 未完成待办保留，预约/退避到期再投递 |
| Kafka 消息超出保留期或消费进度重置 | 未完成待办仍会重投；不能只依赖旧消息还在 broker |
| 消费者收到消息后退出 | 数据库待办未完成，消息重投或租约恢复 |
| Redis 长时间不可用 | 未完成任务退避保留、报警；不承诺旧值到时自动消失 |
| 消息重复、迟到或不同事件乱序 | DONE 跳过；未完成事件只失效，不写回旧快照 |
| 失效与旧重建并发 | 原子撤销锁，旧 token 无法发布 |

持久化数据库丢失、待办被人工删掉、绕过协议直接改库等不在自动恢复保证内。运维直接改库必须同步安排失效；不在本模块引入 CDC。

## 9. 方案对比及选择理由

| 方案 | 优点 | 问题或成本 | 本模块取舍 |
|---|---|---|---|
| 事务内更新数据库再 DEL | 简单 | 删除发生在提交前；Redis 不随 MySQL 回滚；远程等待拉长事务 | 替换 |
| 提交后直接 DEL，失败仅记日志 | 正常路径短 | 进程退出或失败后丢失后续工作 | 不单独采用 |
| 提交后 DEL，失败直接发 Kafka | 利用现有 MQ 削峰重试 | 提交至发送存在故障空隙；异步失败容易遗漏 | 增加同事务 Outbox |
| 同事务待办，后台直接执行 Redis | 组件少，恢复逻辑清晰；模块二已采用 | 缓存工作不能利用 MQ 消费体系 | 技术上可行，本模块为对应简历 MQ 能力选择 Kafka |
| 同事务待办，快速失效 + Kafka 消费 | 正常路径及时；提交后有恢复依据；任务进度可查 | 增加数据库写入、扫描、领取与完成更新，以及消息运维 | 本模块选择，不声称减少数据库写入 |
| 固定延时双删 | 容易理解与实现 | 固定延时不能覆盖任意慢查询或进程退出 | 用原子撤销重建资格处理已讨论的回填竞争 |
| 消息直接覆盖缓存 | 可减少后续回源 | 旧快照迟到可能覆盖新数据，还要维护版本次序 | 商家补偿只失效 |

具体收益：提交后退出也能恢复；Redis 失败不会使已提交商家修改误报失败；Kafka 发送成功与业务完成明确区分；重复消息不会恢复旧商家数据；在途旧重建无法在失效后发布；任务年龄、错误和重试次数可以观察。

成本同样明确：数据库和消息写入增加、链路更长、仍有短暂旧值、异常时期可能反复重建，并且可靠性依赖持久化和后台最终恢复。这是一致性与恢复性方案，不是强一致或性能无成本方案。

## 10. 与其他模块及简历的衔接

模块三提供的安全发布 Lua 与本模块失效 Lua必须配套部署。写入后失效同时清理空值和刷新退避，新增商家也执行相同协议；所有可发布详情缓存的路径都要检查 token，不能留下旧版无条件 SET。

模块三第 9 节的 TTL 分歧已在此解决：保留无物理 TTL 的真实缓存策略，简历删去 TTL 兜底。模块五加入 Caffeine 后，还需要单独讨论各实例本地缓存的失效传播；当前同一 Kafka consumer group 只分发给一个消费者，不能直接当作每个实例都收到的广播方案。本模块不提前宣称覆盖本地缓存一致性。

已有 `CacheManager` 还被秒杀代码调用。改造时只迁移商家链路及其专用消费者，核对依赖后再移除商家旧更新消息路径，不擅自删除影响模块一的代码或用详情失效逻辑清理控制库存。

方案落地并通过验证后，简历可写：

> 数据库事务提交后删除缓存，通过事务 Outbox 和 Kafka 补偿重试，实现缓存与数据库的最终一致性。

需要更具体时可补充“通过 Lua 撤销在途重建资格，避免旧值回填”。当前只有设计文档，不能把这些能力描述为已经实现或已通过压测。

## 11. 修改顺序与验收

| 顺序 | 修改范围 | 完成依据 |
|---|---|---|
| 1 | 增量建表、待办实体/Mapper、写入事务服务 | 商家修改与任务共同提交；失败共同回滚；新增入口能失效空值 |
| 2 | 权威失效 Lua、共享执行服务、提交后快速路径 | 失效先于/晚于重建发布都不残留旧回填；Redis 失败不误报已提交更新失败 |
| 3 | 有界扫描、投递预约、生产者确认与消息协议 | 发送前后退出可重投；迟到回调不能覆盖消费进度 |
| 4 | 条件领取、短租约、单次消费、持久化退避 | 重复跳过、过期恢复；失败安排不靠休眠与未实现的再发送 |
| 5 | 格式切换与旧路径下线、并发/故障验证 | 与模块三统一发布协议；不误伤秒杀或登录数据 |

建表使用非破坏性增量 SQL，不重新导入带删表语句的完整初始化脚本。受控切换时暂停旧商家写入口，部署统一的重建与失效协议，清理旧商家详情缓存后恢复，沿用模块三的安全前缀分批处理规则。不混跑仍会无条件回填或提交前失效的旧版本，不扫描删除其他业务 Key。

必须验证：

1. 事务回滚时商家和待办都未提交，且没有提交前的缓存失效。
2. 事务提交后立即退出，恢复后仍能完成待办；待办插入失败不能只留下商家修改。
3. Redis 删除异常、超时、结果未知时更新仍成功且待办保留；数据库提交未知不伪装为成功。
4. Redis 成功但完成更新失败，重复执行安全；有效租约失联可恢复，旧执行者不覆盖新进度。
5. 旧任务读值后暂停，与数据库更新和失效交错，迟到发布被拒绝；空值发布同样受保护。
6. Kafka 确认不完成任务；发送前退出、发送后回调前退出、消费后确认前退出均可恢复。
7. 发送回调晚于消费者领取/完成时，不覆盖任务状态；预约到期仍未消费的任务可重投。
8. 消费失败后退避生效，重复旧消息不提前重试；数据库状态无法确认时不无条件 ack。
9. 连续修改同一商家、消息乱序或重复，只会失效而不会恢复旧快照；DONE 消息跳过。
10. 数据库长事务旧快照或延迟副本不进入重建回源路径；新建商家清除空值及旧退避标记。
11. Kafka/Redis 长时间不可用后恢复，积压能逐步消化；并发和发送量有界，未完成记录不被重试上限或清理任务删除。
12. 真实商家缓存依旧无物理 TTL，不把 30 分钟逻辑过期写成固定一致性收敛承诺。

使用真实 MySQL、Redis、Kafka 进行事务与故障恢复验证；通过可控暂停制造并发顺序，不仅依靠 mock 验证调用次数。观察到期待办积压、最老未完成年龄、投递/执行次数及耗时、租约恢复、重试错误、失效后重建次数和数据库扫描执行计划。
