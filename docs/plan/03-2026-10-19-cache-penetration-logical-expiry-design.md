# 模块三：缓存穿透与逻辑过期设计

日期：2026-10-19。

状态：核心方案已逐项讨论确认，本文补齐技术衔接和验收要求，待整体审阅；尚未修改业务代码或执行测试。参数是初始配置，不是实测性能结论。

## 1. 目标与范围

围绕商家详情 `ShopServiceImpl.queryById`，将现有空值缓存与逻辑过期整合为同一条可实际使用的查询链路，覆盖正常命中、热点过期、首次加载、数据不存在和依赖故障。

适用数据是商家名称、地址、营业时间等展示信息，允许暂时返回旧值。不用于秒杀控制库存、购买资格、订单状态或支付判定，也不将 GEO 查询、列表查询一并改造。

模块顺序保持为：01 秒杀资格与异步订单可靠性、02 支付与超时关单、03 缓存穿透与逻辑过期、04 缓存一致性与消息补偿、05 Caffeine + Redis 二级缓存、06 多维度滑动窗口限流。

## 2. 现状与主要缺口

- 商家详情实际调用 `queryWithPassThrough`，已经支持空字符串缓存，但没有接入逻辑过期。
- `queryWithLogicalExpire` 已有雏形，但将缓存完全缺失直接视为不存在，无法自行完成首次加载或淘汰后的恢复。
- 后台刷新查到空结果时仍写入逻辑过期包装，未统一表达“数据库确认不存在”。
- 锁固定写入 `1`，释放时直接删除，可能误删其他任务后来取得的锁。
- 锁到期后的旧任务仍能写入缓存，可能覆盖后续重建结果。
- 固定线程池的等待队列没有容量上限；提交失败、任务排队到锁已失效等分支需要处理。
- 另一个 `queryWithMutex` 使用递归重试，且未取得锁的路径也可能执行解锁；不能直接作为本模块的冷加载实现。

## 3. 已确认的行为

| 情况 | 行为 |
|---|---|
| 有真实数据，逻辑上尚未过期 | 直接返回缓存 |
| 有真实数据，逻辑上已过期 | 返回旧数据；争取由一个任务后台刷新 |
| 缓存完全缺失 | 受互斥锁保护加载数据库，其他请求短暂等待并重读缓存 |
| 命中有效空值标记 | 返回商家不存在，不查询数据库 |
| 数据库查询成功且结果为空 | 写入有效期 2 分钟的空值标记 |
| 数据库异常或超时 | 不写空值，不误报商家不存在 |
| 后台执行器无法接收任务 | 返回本次已读到的旧数据，放弃本次刷新并安全释放自己的锁 |
| 刷新失败 | 保留旧数据，约 5 秒后才允许再次尝试刷新 |
| Redis 不可用，无法读取缓存 | 快速返回暂时不可用，不直接回源数据库 |

真实商家缓存采用 **30 分钟逻辑有效期，不额外设置旧数据使用上限**。逻辑过期后继续返回旧数据并尝试刷新；数据库持续故障时，旧数据可能被长期使用，这是已接受的可用性与新鲜度取舍。没有访问时不主动刷新，应用启动不要求全量预热。

本阶段真实商家缓存不设置物理 TTL；空值标记仍设置 2 分钟物理 TTL。30 分钟到期不会自动删除真实数据。5 秒是失败重试退避，不是新的数据有效期，也不是要求用户等待 5 秒。

## 4. 缓存表示与查询结果

沿用商家缓存键前缀 `cache:shop:` 和现有 `RedisData` 包装思路：真实数据保存业务对象与逻辑过期时间，空值使用空字符串并设置物理 TTL。统一读取顺序：Redis 返回 null 表示完全缺失；空字符串表示已确认不存在；非空字符串才解析包装对象。

逻辑时间在成功重建、准备发布数据时重新计算，不能在排队前就开始消耗 30 分钟。应用节点应保持时间同步；时间偏差可能影响刷新时机，不作为库存或支付正确性依据。

Service 必须区分“查到商家”“确认不存在”“繁忙或依赖故障”，不能把超时、锁等待耗尽、反序列化异常或 Redis 故障都转成 null，再统一返回店铺不存在。保留现有 Result 风格即可，不要求在本模块统一改造全项目响应协议。

缓存格式损坏按异常处理并记录，不能当作空值；恢复由安全失效或运维清理处理，不在异常解析路径无限重试。

## 5. 缓存完全缺失时的受控加载

1. 尝试取得当前商家的重建锁；每次取得锁使用新的唯一 token。
2. 拿到锁后再次读取缓存。其他任务可能已经写入，命中则直接使用并安全释放自己的锁，避免重复查询数据库。
3. 缓存仍缺失时，检查该商家的短暂失败退避标记；退避期间不回源，返回暂时不可用。
4. 允许回源时查询数据库。真实结果发布为逻辑过期缓存，明确空结果发布为空值标记；两种发布均须原子校验锁归属。
5. 没拿到锁的请求使用有截止时间的循环，约每 50 毫秒重新读取缓存，最多等待 500 毫秒；等待期间锁释放且仍有预算时可再次竞争，始终先遵守退避规则。
6. 等待结束仍没有可确认的结果，返回繁忙，不自行绕过锁回源，也不返回不存在。中断时恢复线程中断状态并退出，不递归调用。

500 毫秒限制的是等待其他任务的预算，不是负责查库请求的总耗时。数据库查询超时初值建议 2 秒，Redis 单次命令超时初值建议 200 毫秒；须核对当前驱动及客户端配置是否真正生效。轮询间隔和命令耗时可能使实际墙钟耗时略超等待预算，不承诺严格 500 毫秒端到端响应。

冷加载查库失败也设置同一商家的 5 秒退避，避免故障期间连续回源；没有旧数据的请求在退避期返回暂时不可用。退避不产生“商家不存在”的语义。

## 6. 逻辑过期后的后台刷新

请求已经获得旧数据时，先检查刷新退避状态，再尝试取得商家级重建锁。未取得锁或处于退避期，直接返回旧数据，不为锁等待。

取得锁后使用受 Spring 生命周期管理的有界执行器提交后台任务，初始配置为固定 10 个工作线程、等待队列最多 100 个任务，饱和时明确拒绝。不使用将刷新任务转交请求线程执行的 CallerRuns 策略，也不丢弃任务却保留无人释放的锁。应用关闭时停止接收新任务，配合锁租约完成恢复。

提交失败时仅安全释放自己的锁并记录拒绝指标，本次请求继续返回旧数据。排队占用锁租约；任务开始时必须先核对自己仍持有锁，已经失去锁就退出，不能继续查询数据库。初始锁租约为 10 秒，正确性不依赖查询总能在租约内完成。

后台任务开始后再次读取缓存并检查是否仍需刷新，避免在其他路径已刷新后继续回源。重读若已变成有效空值或新鲜数据，则结束；若数据被删除、格式异常或 Redis 不可用，不把先前读到的旧快照重新写回。缓存删除后的恢复交由当前冷加载流程，删除与在途重建的完整协调属于模块四。

正常查询结束后，成功结果写入新的逻辑有效期；明确查到不存在则写 2 分钟空值标记，避免已删除商家永久残留旧值。刷新失败保留原值，原子记录约 5 秒退避并释放自己的锁；期间访问只返回旧数据。退避到期后由后续访问触发重试，不另建定时轮询任务。

若初始读取已经成功、随后刷新辅助操作遇到 Redis 异常，本次仍可返回手中已有的旧数据；“Redis 故障快速失败”针对没有可用数据可返回的请求。无法确认锁归属或失败标记是否落地时，不执行无条件写入、解锁或直接回源，以租约到期恢复。

## 7. 锁归属与写入保护

锁键继续按商家区分，使用 `SET NX` 和租约。冷加载与异步刷新共用同一商家锁，避免两条路径互相绕过。token 按每次锁获取生成，不能只使用固定值或把线程 ID 当作可跨任务重复使用的获取标识。

Redis Lua 提供下列原子操作：

- 安全释放：只有锁值等于本次 token 才删除。
- 发布结果：只有锁值等于本次 token 才写缓存、清理失败退避标记并释放锁；包含真实结果和空值结果两种模式。
- 刷新失败：只有仍持有本次锁才设置短退避标记并释放锁，旧任务不能覆盖新任务的状态。

“仍持有锁”检查与写入必须在同一 Lua 中，不能先 GET 判断、再由 Java 单独 SET。A 的锁到期、B 完成新刷新后，迟到的 A 无权覆盖缓存或删除 B 的锁。丢失锁的任务放弃自己的结果，冷加载请求在剩余预算内重读确认结果，否则返回繁忙。

将 JSON 序列化等准备工作放在 Lua 前，脚本保持短小；必要的类型及参数校验放在变更前。Lua 原子执行不意味着运行时错误会自动回滚已经发生的写入。当前设计针对项目现有单 Redis 实例，不能直接宣称已支持 Redis Cluster 跨槽多键脚本。

客户端收到发布超时不能确定写入未发生；可以在有限预算内重新读缓存确认，无法确认则返回暂时不可用，不误报不存在或进行无条件补写。

本模块防止的是旧锁持有者覆盖新重建结果，**不单独保证数据库更新与缓存重建之间的一致性**。写操作未使用重建锁时，仍可能出现“重建读取旧数据库值、写事务提交并删除缓存、重建随后写回旧值”的竞争；该问题由模块四一起设计。

## 8. 方案对比与收益

| 方案 | 收益 | 成本与适用限制 |
|---|---|---|
| 普通 TTL + 空值缓存，过期直接回源 | 简单，能缓解同一个不存在 ID 的重复查询 | 热点过期时可能大量并发回源，现有入口属于此类 |
| 互斥重建，所有过期请求等待新结果 | 能减少同一热点并发回源，不主动提供过期数据 | 数据库变慢时请求等待增加，仍需有界等待与依赖超时 |
| 逻辑过期 + 后台刷新 + 冷加载互斥，本模块选择 | 有旧值时请求不必等待数据库；首次访问可自行建立缓存；限制后台资源消耗 | 允许旧值；故障时可能长期不更新；需要锁归属、写回保护、退避和有界线程池 |
| 仅预热热点，缓存缺失直接返回不存在 | 查询路径短 | 首次未预热、淘汰或误删都可能误判业务不存在，不采用 |

空值缓存只减少同一个不存在 ID 在 2 分钟内的重复查库，不能彻底拦截不断变化的随机 ID。新建商家可能在空值过期前暂时不可见，写入侧失效将在模块四补齐。请求参数基本校验应保留，布隆过滤器和全局限流不在本模块扩展。

锁只限制同一家商家的重建，不能自动限制所有不同商家的冷加载总并发。有界线程池约束后台刷新，但不能当作全局数据库限流；全局、IP、用户流量治理属于模块六。多实例会增加线程池总容量，需按部署规模评估并配置预算。

本模块选择 Redis 故障时快速失败，避免失去 Redis 锁保护后无约束回源。受控数据库兜底可提高可用性，但要增加独立的并发控制，本阶段不加入；模块五再讨论本地缓存能否帮助读取。

## 9. 与后续模块及旧数据的衔接

模块四负责数据库提交后的缓存失效、删除失败消息补偿，以及失效与在途重建的协调。本模块不把现有事务内直接 DEL 当作最终一致性方案。

**30 分钟逻辑过期不是物理 TTL 兜底。** 模块四已确认保留本模块的选择：真实数据不增加物理 TTL，简历去掉“TTL 兜底”，改为数据库提交后失效、事务 Outbox 和 Kafka 补偿实现最终一致性。详见同目录 `04-2026-10-19-cache-consistency-outbox-design.md`。模块四通过原子失效缓存并撤销当前重建锁，与本模块的 token 校验发布配合，阻止已被撤销的旧任务回填；正常刷新、冷加载及空值发布都须遵守该协议。

模块五加入 Caffeine 时另行确定两级缓存的失效和旧值传播规则，不预先把本模块的结果缓存到本地。

现有真实缓存是裸 Shop JSON，逻辑过期后是 RedisData 包装，不能把旧值直接按新格式解析。实施采用受控切换：暂停旧版本相关读写入口、部署统一读写格式，在受控窗口按商家缓存前缀分批清理旧展示缓存后恢复服务；不得 FLUSHDB，不清理秒杀、订单、登录或 GEO 控制数据。可选预热少量热点，但预热不是正确运行的必要条件。若部署必须滚动发布，应先另行确认兼容读取及失效策略，不混跑互不兼容版本。

## 10. 修改顺序与验收

| 顺序 | 修改范围 | 核对重点 |
|---|---|---|
| 1 | 统一缓存包装、结果区分和配置 | 未命中、空值、异常不会混淆；真实值 30 分钟逻辑过期，空值 2 分钟物理过期 |
| 2 | 每次获取的锁 token、安全发布/释放/失败退避 Lua | 不误删锁；丢锁旧任务不能写回；失败退避不覆盖其他任务 |
| 3 | 有界冷加载循环及有界后台执行器 | 二次检查、500 毫秒等待预算、拒绝提交与排队丢锁处理 |
| 4 | 商家详情接入、受控格式切换 | 不再调用旧的单纯穿透链路；不通过修改入口绕过保护 |
| 5 | 并发与故障验证、观察指标 | 效果以实际结果记录，不把设计收益当作压测数据 |

针对本调用链修正或替换旧方法，避免保留可被新入口误用的递归互斥与不安全解锁逻辑，不扩展为全项目缓存框架重构。

必须覆盖：

1. 正常命中不查库；同一过期热点的并发访问返回旧值，正常租约内只有锁持有者重建。
2. 缓存完全缺失时可加载真实商家；竞争请求在有界等待内读取结果或返回繁忙，不误报不存在。
3. 拿锁后二次检查发现已更新，不再次查库。
4. 数据库成功返回 null 才生成 2 分钟空值；异常、超时不会写空值；空值到期后允许重新查询。
5. 刷新发现商家已删除时转为空值，后续请求不再持续返回旧商家。
6. 锁到期、后续任务取得锁并完成刷新后，旧任务不能覆盖数据或删除新锁；允许超时后有重叠查库，但禁止失去资格的写入。
7. 线程池满、提交拒绝、任务排队到锁失效、任务中断和应用退出时，不出现永久锁或无限任务队列。
8. 数据库持续故障时保留旧值，约每 5 秒才允许该商家新一轮回源；冷加载无旧值时同样退避并返回不可用。
9. Redis 无法读取时不直接回源；读到旧值后刷新辅助操作故障仍可返回该旧值。
10. 发布响应丢失、缓存格式异常、重读失败都不被误判成商家不存在。
11. 真实值没有额外物理 TTL 或旧值上限，逻辑到期会触发刷新而非自动消失；旧格式切换不误伤其他键。

使用真实 Redis 验证 Lua、租约竞争和 TTL，用可控阻塞/故障注入重现迟到写回、队列饱和和依赖超时。记录缓存命中、空值命中、旧值返回、冷加载等待超时、实际查库次数、刷新成功/失败/拒绝、丢锁放弃、执行器队列长度及依赖延迟，必要时对连续刷新失败报警。

以上均为后续实施和验证要求；本次只形成设计文档，尚未实现或执行这些测试。
