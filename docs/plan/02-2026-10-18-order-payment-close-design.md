# 模块二：支付与超时关单设计

日期：2026-10-18。

状态：核心方案已讨论确认，技术衔接及修改范围已补齐，待整体审阅；尚未修改业务代码。本文作为模块设计和后续实施清单的依据。

## 1. 目标与边界

通过模拟支付接口验证支付与关单的并发控制，不接入真实支付渠道，不涉及实际扣款、第三方回调或退款。

待支付订单可以转为已支付或已关闭，两种结果互斥。已支付订单保留库存占用和购买资格；已关闭订单回补库存并释放资格，完成释放后允许用户重新抢购。

本模块针对已经创建、扣过数据库库存的待支付订单。模块一中的“创建失败”终止记录没有扣过数据库库存，不能进入本模块的支付和关单流程，也不能套用本模块的数据库库存回补。

## 2. 已确认的并发控制

- 支付和关单均使用基于旧状态的条件更新，即状态 CAS。
- 支付要求状态仍为待支付，数据库判断时间早于支付截止时间。
- 关单要求状态仍为待支付，数据库判断时间达到或超过支付截止时间。
- 支付期限严格生效，不因为关单任务延迟而允许过期订单继续支付。
- 只有本次成功将待支付改为已关闭的事务，才执行数据库库存回补、数据库购买资格释放和补偿任务插入。
- 影响行数为 0 时，不执行这些副作用；需要区分已支付、重复关单、尚未到期和订单不存在。

`@Transactional` 保证同一个数据库事务内的相关修改一起提交或回滚，不代表支付与关单方法自动串行，也不能自动回滚 Redis 操作。失败必须正确触发事务回滚。

支付有效期初值为订单创建后 15 分钟，可配置；它不同于模块一创建请求的 30 秒处理期限。新增持久化字段 `pay_expire_time`，由创建订单的数据库事务基于数据库时间一次性确定，不随重复消息、支付重试或配置修改而延长。

截止判定采用条件更新 SQL 的数据库语句时间，支付条件为 `pay_expire_time > CURRENT_TIMESTAMP(3)`，关单条件为 `pay_expire_time <= CURRENT_TIMESTAMP(3)`，支付时间使用同一语句的数据库时间。条件更新语句在截止前开始并成功的事务可以在截止后提交；不承诺所有成功支付事务都必须在截止前完成提交。锁等待和事务执行需设置超时，避免长事务拖延结果。

## 3. 已确认的关单调度

采用数据库定时扫描发现到期订单，扫描仅产生候选，是否真正关单由条件更新决定。

为按待支付状态和截止时间筛选、排序及分批处理建立相应联合索引，建议形态为 `(status, pay_expire_time, id)`。限制每批数量、处理线程数和各实例的总扫描及处理频率，避免全量扫描和无限并发。

初值为每 5 秒扫描一次，每批最多 100 条，作为测试起点，不是吞吐或延迟承诺。观察实际扫描行数、查询耗时、数据库锁等待、到期积压和关单延迟后调整。

多个实例可能扫描到同一订单，正确性依靠状态 CAS 和事务，不依赖“任务只执行一次”的假设。

## 4. 可靠释放：数据库待补偿任务表

用户已确认采用“MySQL 待补偿任务表 + 后台重试 + Redis 幂等释放”。

成功关单的同一数据库事务包含：

1. 条件更新订单为已关闭。
2. 回补一份数据库库存。
3. 按用户、券及订单号删除对应数据库购买资格。
4. 插入待释放 Redis 库存和资格的持久化任务。
5. 一起提交；任一步失败则回滚。

新增 `tb_order_compensation_task`，字段包含 `id`、`order_id`、`user_id`、`voucher_id`、`task_type`、`status`、`retry_count`、`next_execute_time`、`claim_token`、`lease_until`、`last_error`、`create_time`、`update_time` 和 `completed_time`。对 `(order_id, task_type)` 建唯一约束，防止同一补偿任务重复生成；对 `(status, next_execute_time, id)` 和 `(status, lease_until, id)` 建索引，分别支持到期待办与超时租约的分批查询。

关单数据库事务中的库存回补和资格删除均校验影响行数。正常成功关单应恰好回补一份库存、删除该订单的一份资格并保存任务；缺失或归属不符视为一致性异常，回滚并记录错误，不静默关闭后继续补偿。

事务提交后，后台分批读取任务并执行 Redis 释放 Lua。Lua 校验当前资格是否仍属于该订单，匹配才回补库存并删除资格；重复释放不重复加库存，也不影响新订单。

Redis 释放成功后标记任务完成；失败时保留任务，按退避策略重试。未完成任务不得因达到普通重试次数而直接删除。重试补偿不再次回补数据库库存，不将已关闭订单改回待支付。

释放 Lua 在同次执行中记录按订单号区分的释放完成标记，回补前校验控制库存 Key 存在、类型正确。再次执行时，有本订单完成标记则返回已释放，不重复加库存；当前资格属于新订单时不改动新资格或加库存。若既没有原资格，也没有可核验的释放结果，则保留任务并报告控制数据异常，不能猜测已释放，更不能盲目加库存。释放完成标记在任务未完成前不得到期；任务确认完成后，才进入可配置保留期。

数据库关单已完成、Redis 释放尚未完成时，区分“订单已关闭”和“资格已释放”，不能提前承诺用户立即可以重新抢购。

## 5. 为什么选择这个方案

这项优化的核心是可恢复性和幂等性，不是减少数据库写入，也不是让 Redis 与 MySQL 成为一个原子事务。

| 对比方案 | 优点 | 存在的问题或成本 | 当前选择理由 |
|---|---|---|---|
| 关单提交后直接调用 Redis，不保存任务 | 实现简单、正常路径短 | 数据库提交后进程退出，或 Redis 失败后重启，可能丢失待释放工作；需要其他方式重新发现 | 单独采用不足以覆盖故障窗口 |
| 在数据库事务里调用 Redis，不保存任务 | 看起来所有操作在一个方法中完成 | Redis 不参与该数据库事务；数据库回滚不会撤销已经成功的 Redis 释放，网络等待还会拉长持锁时间 | 无法靠注解获得跨存储原子性 |
| 关单提交后直接发送 Kafka 补偿消息 | 可利用现有消费能力削峰，适合较大任务量 | 数据库提交与消息发送之间仍存在故障空隙；单纯发消息不能保证补偿任务不丢 | 如后续改为事务内保存 Outbox 再投递 Kafka，也可成立，但本阶段无需增加这一层 |
| 同一数据库事务保存待补偿任务，后台执行 Redis Lua | 关单成功就有恢复依据；应用重启可继续；支持安全重复执行 | 增加任务插入、查询、完成更新及积压治理；Redis 恢复依旧存在延迟 | 本模块已选择数据库扫描调度，可沿用同类机制，以较少组件覆盖关键故障窗口 |

具体收益：

- 消除“数据库已关单，但应用没来得及记录 Redis 待办”的进程故障空隙。
- Redis 暂时不可用时，待办保留在 MySQL，应用恢复后可继续处理。
- Redis 已释放、数据库任务尚未完成时重启，重复执行不会重复回补库存。
- 旧订单的迟到补偿不会删除新订单的资格。
- 可以查询未完成任务、重试次数和任务年龄，发现释放延迟。

上述恢复能力以数据库提交与持久化正常、任务保留以及工作进程最终恢复为前提，不承诺 Redis 持续不可用时也能按时释放。

## 6. 必须覆盖的验证场景

- 支付与关单并发，同一订单只能从待支付转向一个结果。
- 支付已成功时，关单不回补库存、不删除购买资格。
- 关单重复执行时，数据库库存只回补一次，补偿任务只产生一份。
- 关单事务中间失败，订单、库存、购买资格和任务全部回滚。
- 数据库关单提交后立即退出应用，重启后仍能找到释放任务。
- Redis 操作成功但任务完成更新失败，重试不重复加库存。
- 旧订单释放完成后新订单已占用资格，旧任务重试不影响新订单。
- 关单任务延迟时，过期订单依然不能支付。
- 故障积压时扫描和重试受到批量与并发上限约束，不以无限重试冲击数据库。

本节是验证要求，尚未执行测试，不代表已有功能通过验证。

## 7. 已确认的支付接口规则

支付接口要求登录，核对订单归属，不能只凭客户端提交的订单号修改状态。支付条件更新同时约束订单号、当前用户、待支付状态和支付截止时间，成功时记录支付时间。

| 订单情况 | 行为与响应 |
|---|---|
| 属于当前用户、待支付且未过期 | 尝试状态 CAS，提交成功后返回支付成功 |
| 已支付，同一用户再次请求 | 返回已支付成功，不重复改变状态或执行副作用 |
| 待支付但已过期，或已关闭 | 拒绝支付，不回补库存；库存回补由成功关单的事务负责 |
| 订单不存在或不属于当前用户 | 拒绝操作，不泄露他人的订单状态 |
| 模块一的创建失败记录 | 拒绝支付，不转换为待支付或已支付 |

条件更新影响 0 行时，在需要区分结果时读取当前用户自己的数据库订单状态，不能一律解释成系统失败。支付事务提交结果未知时不能假报成功或失败，应提示确认中并允许同订单重试核对；只有已提交的已支付状态才作为支付成功依据。

## 8. 已确认的任务执行与恢复方案

采用“条件领取 + 短租约 + 退避重试 + Redis Lua 幂等释放”，优先减少重复执行，同时允许故障后安全重做。

任务状态分为待执行、执行中和已完成。后台有限批量查找到期任务，通过数据库条件更新领取；只有领取成功的工作者执行 Redis 操作。领取是短数据库操作，执行 Redis 期间不持续占用数据库事务或行锁。

领取时记录本次领取标识和租约截止时间。工作者重启或失联后，其他工作者可重新领取租约已到期的任务。标记完成或安排重试时必须匹配本次领取标识及执行中状态，防止旧执行者覆盖新执行者的任务状态。

| 执行或恢复结果 | 任务状态处理 |
|---|---|
| Lua 确认本次释放成功，或本订单已释放 | 匹配领取标识后标记已完成 |
| 当前资格属于另一个新订单 | 不动新资格、不加库存，按安全空操作标记已完成 |
| Redis 调用失败、超时或结果未知 | 匹配领取标识后改回待执行，记录原因并安排退避重试 |
| 原资格和可核验的释放结果均不存在，或控制 Key 缺失、类型错误 | 不加库存、不宣告完成；保留任务并退避，同时输出一致性异常供核对 |
| 执行者失联，任务仍为执行中且租约到期 | 其他工作者通过条件更新重新领取，生成新的领取标识 |

领取数量不得超过当前可执行的工作容量，避免先批量领取、再在队列中等待到租约失效。任务批量查询上限不等于一次性领取数量。

租约减少重复调用，但不能保证绝对不重复执行；正确性由释放 Lua 对订单归属的检查与幂等处理保障。客户端超时、执行延迟或租约到期后重做，都不能重复回补库存或误删新订单资格。

失败重试采用退避策略，初始间隔为 1 秒、5 秒、30 秒，随后以 60 秒为间隔继续重试，并限制工作线程、批量大小及数据库和 Redis 调用量。持续失败记录错误并输出可观测指标，保留未完成任务，不因为达到普通重试次数而删除。租约初值为 30 秒，Redis 单次调用超时初值为 2 秒，均可配置；正常调用应在租约内完成，但安全性不依赖这一时长假设。领取后不在工作线程中长时间休眠，失败时更新下一次执行时间。

方案对比：直接读取并执行任务可依靠 Lua 保证安全，但多个实例会产生较多重复调用；条件领取和租约增加领取、重试及完成更新成本，换取较少重复调用和可恢复的工作分配。数据库持锁执行 Redis 会拉长事务，本方案将任务领取与远程执行分开。

幂等在本模块中的具体含义：同一关单或释放操作即使执行多次，最终业务效果仍与成功执行一次相同。第一次操作可能修改一行，后续操作可能返回已完成或影响 0 行，返回内容不必完全相同。数据库关单靠状态条件更新防止重复回补；Redis 释放靠同订单号资格检查和原子释放防止重复加库存。

## 9. 与模块一及查询接口的衔接

模块一的请求结果只表示订单是否创建成功，一旦订单成功创建，后续支付或关单不把这个创建结果改为失败。订单生命周期以 MySQL 的订单状态为准，不能拿 Redis 中的“创建成功”判断订单仍可支付。

保留模块一的 Redis 请求进度查询；新增当前用户订单详情查询，从 MySQL 读取订单状态、支付截止时间、支付时间。订单关闭时结合补偿任务返回 `releasePending`，区分“已关闭，资格释放中”与“已关闭，资格已释放”。详情查询是独立接口，要求登录和归属校验，限制轮询频率，不把模块一所有处理中请求的轮询改成查库。

支付成功或关单完成后，前端停止支付倒计时并更新订单状态；未确认提交结果时显示确认中并查询订单，不假报成功或失败。请求重复或网络恢复后重新进入页面，仍以服务端状态为准。

重复创建消息在发现订单已经支付或关闭时，只认定该订单曾创建成功，不重建资格、不再次扣库存、不恢复待支付状态。迟到的模块一结果回写只能更新创建结果，不能覆盖本模块的生命周期或重新添加资格。旧订单的补偿任务按旧订单号释放，不删除后来重购的新资格。

本模块仅提供模拟支付、订单详情、内部超时关单和补偿恢复，不额外加入主动取消订单、退款、真实支付回调或订单列表等功能。

## 10. 修改清单与实施检查点

| 检查点 | 修改范围 | 验证后再推进 |
|---|---|---|
| 1. 数据模型与支付 | 增量 SQL、订单实体和状态常量、支付与详情 Controller/Service/Mapper | 截止时间固定；归属正确；重复支付不重复修改；创建失败记录不能支付 |
| 2. 事务关单 | 条件关单、数据库库存回补、按订单删除数据库资格、补偿任务实体和 Mapper | 支付与关单互斥；失败全回滚；重复关单只有一次回补及一份任务 |
| 3. 调度与释放 | 索引扫描任务、条件领取与租约、共享释放 Lua 的完成标记、退避调度 | 重启可恢复；释放重试不多加库存；租约重领后旧工作者不能覆盖任务状态 |
| 4. 模块衔接 | 模块一重复消费结果处理、创建结果与订单状态分离、前端必要状态显示 | 已关闭不被旧消息复活；资格释放中不承诺可重购；端到端重新抢购成功 |

参数由配置管理，订单截止时间一经创建不随配置改变。补偿领取扫描初值为每秒一次、每批最多 100 条、单实例最多 2 个工作线程；关单处理也使用有界执行器，禁止在应用实例增加时无上限放大处理能力。具体全实例预算随部署实例数配置并通过积压测试验证。

提供非破坏性增量迁移，不重新导入包含删表语句的完整 SQL。启用前暂停旧订单写入，核对并补齐既有待支付订单的截止时间和模块一数据库资格；重复、缺失资格或无法确认是否扣过库存的历史记录先人工核对，不自动回补。新增创建失败状态与既有状态编码保持区分。

未完成补偿任务不自动删除；已完成任务及其释放标记的保留期联动管理。Redis 控制数据丢失时沿用模块一的停止受理与核对恢复规则，不能借补偿任务按数据库剩余库存直接覆盖 Redis 预扣库存。
