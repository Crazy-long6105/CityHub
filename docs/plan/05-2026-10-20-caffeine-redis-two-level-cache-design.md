# 模块五：Caffeine + Redis 二级缓存设计

日期：2026-10-20。

状态：结合前四个模块的取舍完成设计，尚未修改业务代码或执行测试。参数为实施初值，需压测后调整。

## 1. 目标、范围与顺序

在商家详情查询上增加 Caffeine 本地缓存，形成“进程内缓存 → Redis → MySQL”的二级缓存，减少热点请求访问 Redis 的次数，同时保留模块三的缓存穿透、逻辑过期和受控冷加载，保留模块四的提交后失效与补偿。

本模块只接入 `ShopServiceImpl.queryById` 的商家详情。商家列表、GEO、秒杀库存、购买资格、订单和支付状态不放入本地缓存；分类等其他展示数据另行评估。模块顺序为 01 秒杀可靠性、02 支付关单、03 穿透与逻辑过期、04 一致性与消息补偿、05 二级缓存、06 滑动窗口限流。

## 2. 两级读取路径

```text
请求
  └─ Caffeine L1 命中 → 返回
  └─ L1 未命中 → Redis L2（按模块三规则处理）
                    └─ 命中 → 回填 L1 → 返回
                    └─ 未命中 → 受控查询 MySQL → 回填 L2 和 L1
```

L1 只保存已经从 Redis 或数据库确认得到的结果，不绕过 Redis 的空值、逻辑过期和锁协议。Redis 返回逻辑过期的旧商家时，可以回填 L1，但 L1 的本地有效期必须短于 Redis 的逻辑刷新周期，避免一个实例长期遮蔽 Redis 的刷新结果。

L1 命中不代表数据库强一致。商家修改提交后，先由模块四失效 Redis 和本地缓存事件；在失效消息到达前，某个实例仍可能返回已读到的旧值。模块五的本地短 TTL 是失效通知丢失时的上限保护，不改变模块四最终一致性的边界。

## 3. Caffeine 配置和缓存内容

引入 Caffeine 依赖和 Spring 生命周期管理的 `Cache<String, LocalShopValue>`。初始配置：

- 最大条目数 10,000，按实例内存和热点数量压测调整。
- 真实商家 `expireAfterWrite` 30 秒，作为本地旧值上限；不使用永久保留。
- 明确不存在的商家使用负缓存标记，初始 2 秒；Caffeine 不直接存 Java `null`。
- 不使用 refreshAfterWrite 的后台线程作为唯一刷新机制；Redis 逻辑过期刷新仍由模块三负责。
- 加入命中、未命中、驱逐、加载失败和占用内存观察指标。

30 秒只限制 L1，Redis 真实数据仍按模块三的 30 分钟逻辑有效期且没有物理 TTL。L1 的更短有效期会增加 Redis 读取次数，但能减少本地缓存错过失效通知时的陈旧时间。Caffeine 超出最大容量按其驱逐策略删除，删除后重新走 Redis。

建议把本地值包装为明确类型：真实 `Shop`、确认不存在的负标记及必要的逻辑过期/版本元数据。不能用空对象冒充不存在，也不能把数据库异常写成负标记。写入和返回前复制或只读化 Shop，避免 Controller 修改对象后污染所有后续请求；`distance` 等请求特有字段不能写入详情缓存。

## 4. L1 未命中和并发加载

L1 未命中时直接调用模块三的 Redis 读取服务；Redis 命中真实值或空值后才回填 L1。多个线程同时 L1 未命中时，不能让每个线程都访问 Redis：以商家 ID 为键使用 Caffeine 的单键 `get(key, mappingFunction)` 或等价的有界请求合并，但 mapping 函数内部仍必须遵守 Redis Lua 锁和冷加载等待预算。

请求合并只限制当前 JVM，不能替代 Redis 分布式锁。加载函数异常不得缓存异常结果；加载超时/繁忙不得写负缓存。L1 回填失败不影响已经从 Redis 得到的响应，后续请求重新尝试。

Redis 无法读取时，L1 命中仍可返回本地值；L1 未命中遵循模块三选择，快速返回暂时不可用，不直接绕过 Redis 查询数据库。这个变化是二级缓存的可用性收益，不把 Caffeine 当作秒杀控制数据的容灾来源。

## 5. 多实例失效传播

本地缓存是每个应用实例独立的，模块四的 Kafka 同一个 consumer group 只能让一个实例收到某条消息，不能直接用作广播。因此商家失效任务完成 Redis 失效后，需要同时通知每个实例清理同一 L1 键。

本阶段选择 **Kafka 广播消费者 + 本地短 TTL**：

1. 为每个应用实例配置稳定且唯一的广播 consumer group 标识（由部署实例身份生成并持久化），所有实例都订阅商家 L1 失效事件。
2. 失效事件只携带商家 ID/事件 ID，不携带旧商家 JSON；实例收到后删除对应 Caffeine 键，再确认消息。
3. 消费成功后记录最近处理的事件 ID，重复事件只重复删除，不产生业务副作用。
4. 实例启动时清空本地缓存并从最新事件开始消费；本地 30 秒 TTL 作为重启/丢通知后的有限兜底。若必须保证重启后不漏历史失效，额外做一次按事件 ID 的小批量数据库对账，不能假称 Kafka 最新位点覆盖历史。

广播消息与模块四的“待办是否完成”分离：Redis 失效成功才能把数据库待办标记 DONE；某个 L1 广播实例暂时不可用，不应回滚已经提交的数据库更新或阻塞 Redis 失效。广播事件要有可恢复的发送依据（可复用失效任务的事件记录并按事件 ID 重发），不能只依赖请求线程的一次 best-effort 发送；即使发布结果未知，重复删除也必须安全。L1 TTL 仍是广播长期丢失时的有限兜底，持续失败记录指标并报警。

这里的稳定 group ID 需要运维提供实例身份；实例身份重复会导致两实例分摊消息，失去广播效果。若部署平台无法提供稳定身份，应改用 Redis Pub/Sub 加启动对账，或改成每次请求按版本对账；在实现前必须确认部署约束，不能默认随机 group ID 就可靠广播。

失效事件只能删除 L1。它不写入新值、不依赖消息顺序；更新事件乱序时，后来的查询从 Redis/数据库读取当前值。模块四的 Redis 失效 Lua 仍需撤销在途重建资格，避免 L2 重新填入旧值后被 L1 回填。

## 6. 更新与删除规则

商家更新仍由模块四的数据库事务 Outbox 驱动。事务提交后执行权威 Redis 失效；Redis 失效确认成功后发布 L1 广播删除事件。为降低时间窗口，提交后快速路径可以先向本机 L1 删除，但这只是优化，不能代替模块四的权威失效；如果 Redis 失败，Outbox 仍保留。

L1 删除是幂等的：键不存在或重复删除都算本机处理成功。L1 删除事件处理异常时不要用旧消息写缓存；通过 Kafka 重投/该实例恢复和 30 秒 TTL兜底，必要时报警。删除通知不携带对象快照，避免迟到事件覆盖新数据。

新增商家沿用模块四清理空值标记的协议，再允许查询回填两级缓存。不存在的商家 L1 负缓存只有 2 秒；Redis 空值标记 2 分钟。商家新建后可能在 Redis 空值 TTL 内不可见，这是模块四已知的最终一致性取舍，必要时写入成功后主动失效并广播。

## 7. 方案对比与收益

| 方案 | 收益 | 问题/成本 | 当前选择 |
|---|---|---|---|
| 只有 Redis | 结构简单、实例间天然共享 | 每个热点请求都访问 Redis，Redis 网络和连接压力较高 | 作为现状对照 |
| Spring Cache 注解 + Caffeine | 接入较快 | 默认语义难以表达逻辑过期、空值、失效事件和异常，容易把第三模块规则藏起来 | 不直接采用 |
| Caffeine L1 + Redis L2，共享加载/失效服务 | L1 热点命中减少网络跳转；L2 继续共享；边界和故障策略可观察 | 增加本地内存、广播失效、实例身份和短 TTL 调优 | 本模块选择 |
| 只靠每实例定时清空 L1 | 实现简单 | 清空窗口大，更新后仍可能长期读旧值；全量清空浪费热点 | 不采用 |
| L1 永久缓存、只靠 Kafka 失效 | 命中率高 | 漏消息或实例重启会长期旧值，无法接受 | 不采用 |

实际收益需要压测确认，不能直接写成固定百分比。至少观察 Redis QPS、L1 命中率、响应延迟、堆内存、驱逐次数、广播延迟及失效后重建次数。L1 会让单实例命中更快，但多实例总内存和广播运维成本增加。

## 8. 修改顺序与验收

| 顺序 | 修改范围 | 完成依据 |
|---|---|---|
| 1 | 引入 Caffeine、配置上限/TTL/指标、定义值类型 | 空值、异常、真实值区分；不缓存可变请求字段 |
| 2 | 抽取两级查询服务并接入商家详情 | L1→L2→受控加载顺序正确；单 JVM 并发合并不绕过 Redis 锁 |
| 3 | 将模块四失效事件接入本地删除 | 提交后删除、Redis 补偿与本地删除职责不混淆 |
| 4 | 广播 consumer group、事件去重和启动策略 | 每个实例都能收到；重复/乱序只删除，不写旧值 |
| 5 | 多实例、故障和压测验证 | L1 失效延迟、内存、Redis 压力和 Redis 故障行为有实际数据 |

必须验证：L1 命中不访问 Redis；L1 未命中能命中 L2 并回填；两级都未命中只由受控流程加载；异常不进入负缓存；重复失效安全；某实例漏消息后最多受本地 TTL 影响；实例重启不带着旧 L1 数据继续服务；Redis 故障时 L1 命中仍可用、L1 未命中快速失败；多实例更新后各自 L1 最终清除；失效与模块三在途刷新并发时不会回填旧值。

本模块不修改秒杀库存、资格、订单和支付查询的缓存语义，也不把“本地缓存命中”描述成跨实例强一致。
